# درگاه به‌پرداخت ملت

مرجع پیاده‌سازی، مستند رسمی `ipg-tech-doc.pdf`، نگارش ۱٫۳۸ (شهریور ۱۴۰۴) است. نمونهٔ ووکامرس فقط برای تطبیق قالب SOAP استفاده شده؛ آدرس عملیاتی موجود در آن برای تست استفاده نمی‌شود.

## راه‌اندازی آزمایشی

تنظیمات زیر را در `.env` بک‌اند با اطلاعات **محیط تست صادرشده توسط به‌پرداخت** تکمیل کنید:

```dotenv
MELLAT_SANDBOX=true
MELLAT_TERMINAL_ID=
MELLAT_USERNAME=
MELLAT_PASSWORD=
```

حالت پیش‌فرض تست است. آدرس‌های محیط آزمایشی مطابق مستند رسمی:

- WSDL: `https://pgw.dev.bpmellat.ir/pgwchannel/services/pgw?wsdl`
- SOAP: `https://pgw.dev.bpmellat.ir/pgwchannel/services/pgw`
- صفحهٔ پرداخت: `https://pgw.dev.bpmellat.ir/pgwchannel/startpay.mellat`

مهاجرت‌ها را روی دیتابیس محیط تست اجرا کنید و سرویس بک‌اند را مجدداً راه‌اندازی کنید:

```bash
python manage.py migrate
```

در پنل، تنظیمات درگاه‌ها، «به‌پرداخت ملت» را اضافه کرده و شمارهٔ ترمینال تست را وارد کنید. ترمینال پنل بر `MELLAT_TERMINAL_ID` مقدم است؛ نام کاربری و رمز فقط از تنظیمات سرور خوانده می‌شوند. مهاجرت فقط بانک را به فهرست انتخاب اضافه می‌کند؛ درگاه را فعال نمی‌کند. بدون نام کاربری، رمز و ترمینال معتبر، درگاه در فروشگاه نمایش داده نمی‌شود.

`PAYHUB_PUBLIC_URL` باید آدرس عمومی HTTPS هاب باشد. آدرس بازگشت برای معرفی به بانک:

```text
{PAYHUB_PUBLIC_URL}/mellat/callback/{token}
```

طبق مستند رسمی، دامنهٔ بازگشت باید همان دامنهٔ ثبت‌شده نزد به‌پرداخت باشد و IP سرور و اطلاعات پذیرنده باید برای محیط تست مجاز باشند. مسیرهای `/mellat/pay/…` و `/mellat/callback/…` باید به Django برسند.

قالب‌های nginx پروژه برای این مسیرها به‌روز شده‌اند؛ در محیط تست تنظیمات متناظر را اعمال کنید. زمان انتظار gunicorn و پراکسی حداقل ۱۸۰ ثانیه باشد، چون مسیر بازیابی خطا ممکن است پنج درخواست SOAP سی‌ثانیه‌ای داشته باشد.

## رفتار پرداخت

- کلید درگاه `mellat` است؛ مبلغ بدون تبدیل مجدد، به ریال ارسال می‌شود.
- `orderId` همان شناسهٔ یکتای رکورد پرداخت هاب است؛ هر تلاش جدید برای یک فاکتور، شناسهٔ بانکی جدا دارد.
- مسیر `/mellat/pay/{token}` یک فرم POST با `RefId` می‌سازد. پرداخت از طریق GET مستقیم به بانک شروع نمی‌شود.
- حالت تست و ترمینال هنگام شروع تراکنش ذخیره می‌شوند و برای بازگشت، تأیید، تسویه و پیگیری همان تراکنش استفاده می‌شوند.
- `RefId` با حساسیت به بزرگی حروف و `SaleOrderId` با درخواست اولیه تطبیق داده می‌شوند. اطلاعات نامنطبق هیچ درخواست تأییدی به بانک نمی‌فرستد.
- بازگشت موفق بانک به‌تنهایی سفارش را نهایی نمی‌کند. ابتدا `bpVerifyRequest` و سپس `bpSettleRequest` باید موفق شوند. کدهای ۴۳ و ۴۵ مطابق سند برای تأیید و تسویهٔ تکراری پذیرفته می‌شوند.
- تأیید نامشخص با تکرار تأیید و سپس `bpInquiryRequest` بررسی می‌شود؛ ابهام حل‌نشده وارد مسیر `bpReversalRequest` می‌شود. پاسخ نامشخص تسویه، موفقیت تلقی نمی‌شود و امکان تلاش مجدد دارد.
- فرمان موجود `payhub_reconcile` پرداخت‌های معلق را با متدهای ملت پیگیری می‌کند؛ تسویهٔ بانکی بدون سفارش نهایی برای بررسی کارشناس نگه داشته می‌شود.
- فاکتور پرداخت آزمایشی با `is_test=True` ثبت می‌شود. گردش فعلی پروژه برای فاکتورهای تست (موجودی، اعلان و ERP) برقرار است؛ در نرم‌افزار فروش برچسب تست دارد. برای آزمایش بدون نوشتن در ERP، `ERP_WRITES_ENABLED=false` باشد.
- رمز و بدنهٔ SOAP در رویدادها ذخیره نمی‌شوند؛ شمارهٔ کامل کارت نیز ذخیره نمی‌شود.

سایت قدیم نیز می‌تواند با `gateway=mellat` از `GenerateToken`، سپس `GoToPayPage/{token}/{invoiceId}/{amount}` و `PaymentVerification/{token}` استفاده کند.

## آزمون‌ها

```bash
DATABASE_URL='' .venv/bin/python manage.py test apps.payhub apps.erp.tests.TestPaymentTests --noinput
```

تمام تماس‌های بانکی این تست‌ها شبیه‌سازی می‌شوند. اجرای این آزمون‌ها تراکنش واقعی یا تراکنش در سرور تست بانک ایجاد نمی‌کند. آزمایش سرتاسری در سرور بانک به اطلاعات پذیرندهٔ تست و دامنهٔ مجاز نیاز دارد.
